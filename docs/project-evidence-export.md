# 项目证据包 v2

项目成员可以从“项目知识”页面下载 `project-<id>-evidence.zip`，或调用
`GET /api/v1/projects/{project_id}/evidence/export`。接口先验证登录及项目读取权限；
全局管理员按原有跨项目权限执行。该 ZIP 含项目材料和业务结果，**必须作为敏感资料保管**。
没有额外密码保护，浏览器下载端和后续传输要遵守团队的数据分级要求。

## 包内内容

- `manifest.json`：新版格式 `project-evidence.v2`、项目 ID、名称和模板来源摘要、生成时间、各类型数量、
  每个文件的路径、字节数和 SHA-256。包内散列用于检测意外损坏，**不是签名**。
- `import/`：导入批次字段、原始行、状态和警告；
  `governance-import-files/`：有明确快照路径及 SHA-256 的治理导入原始文件；
  旧记录从未保存原始文件时仅标记 `source_saved=false`，不按名称补造；
  `document/` 与 `document-files/`：提取后的正文、元信息和原始材料。新上传的材料记录上传时
  `source_sha256`、`source_size`，并标记 `creation_integrity=verified`；迁移前旧材料无上传时摘要，
  保持 `unverified`，不会根据当前磁盘内容追认。
- `analysis/`：需求分析结果和版本；`harness_task/`：任务归属、关联 Session ID、
  协议及已完成任务的**已校验业务结果**。不包含 Harness 原始 Session、工具事件、
  模型请求或未经校验的失败输出。
  `analysis_report/<task_id>.md`：已完成且带有原始报告的 Harness 需求分析另行交付
  同字节 UTF-8 Markdown。导出前必须与同项目任务结果及分析快照逐字一致；历史结果
  没有原始报告时不生成该文件，也不从兼容报告补造。
- `draft/`、`case/`：用例草稿与当前用例字段，保留原用例 ID、原值、空值、审核状态、
  版本、治理字段以及仍在库用例的审核/评论历史；`governance_change/` 保留项目治理变更
  的操作、变更前后值和撤销来源 ID，已知用例 ID 与用例建立显式关联；
  `taxonomy/`、`suggestion_job/`、`suggestion/`
  保留项目分类版本、建议任务与逐条建议的来源、候选值和人工决策；
  `duplicate_group/`、`duplicate_member/`、`governance_validation/`、
  `governance_metric/` 保留项目内重复组决策、成员评分、导入前验证和批次指标；
  `governance_directory/` 以目录路径的 SHA-256 为安全文件名保存当前目录状态；
  `governance_export_job/` 保存原治理导出任务的行数、自检和文件摘要，不含服务器文件路径；
  `governance-export-files/` 保存原有导出字节，使用任务 ID 作安全文件名；
  `conversion/`、`conversion-files/`：转换预览元数据和历史结果文件。新生成的结果记录
  创建时 `output_sha256` 并标记 `creation_integrity=verified`；旧记录保留 `unverified`，
  不根据目前的结果文件追认创建时身份；
  `conversion_input/`、`conversion-input-files/`：新版转换记录明确留存的原始上传文件身份、SHA-256 和字节内容。旧版记录没有留存输入字节时不伪造来源节点。
- `smoke_suite/`、`smoke_item/`、`execution_run/`、`run_case/`：当前冒烟集和执行记录，
  包括进行中执行与仍在库的逐条操作事件；
  `execution_report/`：按各自原有 SHA-256 校验的冻结报告，包括原始的历史完整性标记；
  `report_case/`：从已校验报告中逐项复制的冻结用例，文件名为 `<执行ID>-<执行用例ID>.json`，
  业务 ID 仍为 `<执行ID>:<执行用例ID>`；即使当前用例已删除也保留冻结标题、原始 ID、版本与执行结果。
  离线校验会将每项冻结内容与原报告按 JSON 字段和类型核对，并检查报告、源用例、执行用例、
  缺陷关联在索引中是否齐全及 `included` 标记是否正确；不会把历史完整性未验证的报告升级成已验证；
  `defect/`：缺陷当前内容及审计；`knowledge/`：知识当前内容与完整历史版本。
  新建知识引用需求材料时，来源快照还包含创建时已记录的原件 SHA-256 与字节数；
  旧材料未记录摘要时保留 `unrecorded`，不能将快照当作原件已验真的证明。
  新建知识引用转换产物时，来源快照也保留创建时已记录的**转换结果** SHA-256
  和字节数（不是上传输入的摘要）；旧转换记录未存结果摘要时同样标为 `unrecorded`。
  快照记录的是当时的元数据，导出的文件本身仍按证据包规则独立核对。
  新建知识引用已完成的 Harness 任务时，只有持久化结果与任务及已绑定 Session
  一致、并再次通过对应技能的交付 Schema 校验，才冻结结果 ID 和规范化 JSON SHA-256；
  用例任务还须与同项目分析中的需求和验收条件追溯一致，并另冻结建立知识时该原始分析
  的规范化 JSON SHA-256 与分析运行 ID。这些不是 Host 原始响应或模型原始字节的摘要，
  也不能自动证明分析与用例语义正确。旧知识条目不会追溯补算摘要。
  新建知识引用已完成的需求分析时，空结果不再算有效来源；Harness 分析还要逐项
  核对原始结果、项目内来源、已完成的原任务与分析运行归属。快照冻结分析版本、
  Provider、关联 Harness 任务 ID（如有）和当前业务分析结果的规范化 JSON SHA-256；
  业务结果可包含人工决定，摘要不等于 Harness 原始报告字节的摘要。
- `indexes/references.json`：有明确来源 ID 的关系索引。`included=false` 表示关联仍保留，
  但对应产物已不在本次证据包中；用例、分类版本、建议任务与建议记录按 ID 关联；
  新版转换输入通过单次导出的记录 ID 直接关联到转换结果，不据文件名推断旧记录的来源。
  冻结报告通过 `contains_case` 指向每项 `report_case`，后者与仍在库的执行用例、活用例、
  缺陷分别通过 `frozen_as`、`snapshot_of`、`found_defect` 关联；源用例已删除时索引明确标记
  `included=false`，不会凭标题或文件名补造来源。
  `harness_task` 经 `contains_report` 指向 `analysis_report`，后者经 `reviewed_as`
  指向对应 `analysis`；离线校验会逐字比对报告和两份归档 JSON，并验证这两条关系。
  离线校验还对**每条关系的两端**核对类型、ID、`included` 布尔值及包内文件存在性；
  已收录的节点不能标为缺失，未归档的节点不能伪称已收录。`included=false` 的历史来源
  仅表示本包没有对应文件，无法独立证明其归属或当初是否存在。
  新导出使用 `project-references.v2`，离线工具依据包内业务记录重建全部显式关系，
  校验索引没有漏边、增边或重复边；旧 `project-references.v1` 仍可读取，但只校验
  端点收录状态及原有的报告专项关系。命令输出的 `reference_integrity` 分别标为
  `complete` 或 `legacy-membership-only`，不能把旧索引误报为全量关系已核对。

不包含账号、密码、模型供应商配置、API 密钥、Cookie、后台任务提示词、
完整 Harness Session、Codex 会话、外部 Host 私有目录、数据库表结构与迁移状态。
也不是可直接恢复的项目备份：完整恢复需使用数据库、上传目录和 Host 持久目录的
停写备份流程，参见 `docs/harness-backup-recovery.md`。

## 安全与校验

文件名使用数据库产物 ID 而非用户上传的文件名，原始文件名只记录在项目内 JSON。
原始材料、治理快照与导出文件、转换输入及输出仅从项目私有目录读取，拒绝符号链接、junction、缺失文件和读期间
大小变化，并对同一个打开的文件描述符核对读取前后的大小、修改时间和状态变更时间，
同长度的读取期间改写也会使本次导出失败。该检测不能证明旧文件自创建以来未变化，
也不构成数据库加文件系统的原子快照；已留存的转换输入、新生成的转换结果及新上传的需求材料还须与各自记录的
创建时 SHA-256 一致。需求材料、转换输入与转换结果的下载会从校验过的临时快照响应，
避免在校验后重新读取已改变的原文件。旧材料和旧转换结果的下载与证据包明确标记 `unverified`。
一份文件无法安全读取时直接失败，不输出看似完整的部分 ZIP。
治理导入快照会与导入时保存的 SHA-256 比对；新建治理导出任务在创建时保存文件大小及
SHA-256，直接下载、证据导出和离线校验均须与该摘要一致。旧任务没有创建时摘要，
证据包标记为 `creation_integrity=unverified`；对它计算的 SHA-256 只证明本次读取的
文件与包内字节一致，不证明创建后从未被改写。摘要没有外部签名，不能抵抗同时修改
文件与数据库记录的有权限人员。
关系索引和清单都没有外部签名；若有人能够同时修改 ZIP 所有文件及清单，甚至将索引
版本改回 v1，离线格式校验也无法证明原始来源未遭伪造。正式归档须独立保存可信包摘要。
损坏的执行报告也会阻止导出。默认最多 10000 个 ZIP 条目，单文件 128 MiB，
未压缩内容总计 512 MiB；服务器管理员可通过 `TEST_ATELIER_EXPORT_MAX_BYTES`
调整总上限。数据库行在一个读事务中导出：PostgreSQL 使用 repeatable-read，SQLite
显式开始读事务；默认最多持有 300 秒，管理员可用 `TEST_ATELIER_EXPORT_MAX_SECONDS`
调整。超过容量返回 413，超时返回 503，均不提供部分 ZIP；长时间读事务会占用数据库资源，
生产环境须结合实际规模设置预算。这里不是增量或分卷导出。

下载后独立验证：

```bash
python scripts/verify_project_export.py project-1-evidence.zip
```

PostgreSQL 部署可在已运行迁移的临时环境显式执行
`TEST_ATELIER_PG_SMOKE=1 python -m scripts.verify_project_export_pg`：脚本创建并清理独立
项目，并发提交用例改写和新增后生成 ZIP，以离线校验器核对旧读视图；随后
移走该项目的材料文件，确认数据库仍有记录时导出失败。该演练不会
验证上传文件的跨存储原子性。CI 已配置该步骤，是否通过以真实流水线结果为准。

工具逐项校验 ZIP 路径和文件摘要，再次核对报告内的摘要与项目 ID。若管理员提高
总上限，校验时相应提供 `--max-bytes <bytes>`。没有外部签名时，校验通过不能证明
证据未被有权限的人员修改。导出期间若项目仍在变化，数据库行使用同一次读取视图，
但上传文件、治理文件和转换文件是按路径依次读取和核对；没有统一的数据库加文件系统事务，
**不保证整个 ZIP 属于同一时刻**。需要一致的全量恢复归档时必须走停写备份。
旧版 v1 包未记录后来新增类型的零数量、或仅保存治理导出任务元数据时，校验器仍可读取；包中实际存在的类型
必须在 `counts` 中列出并与文件数一致。未找到关联的建议来源会被拒绝为不完整证据。
新版 v2 强制声明 `analysis_report` 类型（即使数量为零）并验证每份可交付报告的
原始字节、来源分析和任务归属；旧版 v1 仅按其当时具备的产物范围验证，不能补称
已有独立 Markdown 交付。ZIP 散列不是防篡改签名，有权限的参与者仍可能同时改写
文件和 manifest，发布评审还应保存可信的包摘要。
